# TSUGU AI 2.0 段階3（実際に使うための安全の土台）計画メモ

仕様の正は Notion。ここには、段階3で何をどの順に作り、何がまだ決まっていないかだけを書く。
**このメモは計画であり、実データを扱ってよいという承認ではない。**

## いまの状態

| 項目 | 状態 |
| --- | --- |
| 権限確認の仕組み（本人 → 役割 → 対象が本人のものか） | 作成済み（`lib/v2/access.ts`）。架空の名簿を使い、処理の単位で検証した。本物の認証・保存先での検証と、操作が同時に重なる場合の検証はまだ |
| 操作の記録（本文を残さない） | 作成済み（`lib/v2/audit.ts`）。メモリの中だけ。改ざんや消去への備えはない |
| 新しく始める回数の上限 | 作成済み（**全体で**1分に30回）。1人が使い切ると、その1分はほかの人も始められない |
| 保存先がいっぱいのとき | 既存の面談は消さず、新しい面談を断る |
| 公開用に組み立てたもの・公開先での停止 | 作成済み。開発用に動かしているとき以外は API が止まる |
| 本物の認証（ログイン、多要素認証、復旧） | **Clerk に決定**（2026-11-15 オーナー決定）。検証用の動かし方（下の「検証用の動かし方」）を作った。**鍵がないので、本物の Clerk では一度も動かしていない** |
| 保存先 | **Turso に決定**（2026-11-14 オーナー決定）。会社ごとにデータベースを分ける。保存先の部品（`lib/v2/store-libsql.ts`）は作成済みで、手元の中だけで動くデータベースで検証した。**本物の Turso にはまだつないでいない**。手元の試作はメモリ保存のまま |
| 本物の AI への接続 | **未着手**。送信条件が未確認 |
| 削除・バックアップ・事故対応の運用 | **未着手**。責任者と期間が未決定 |
| 第三者による診断、個人情報の専門家の確認 | **未着手**。依頼先が未決定 |

手元の試作は、いまも「ログインなし・メモリ保存・モック」のまま。公開先では API が止まる。

**「いまの備え」の読み方**：下の表の備えのうち、ログアウト・期限切れ・所属・役割に関するものは、検証用の名簿（架空の利用者）で確かめた仕組みの動き。手元の試作にはログインがないので、ログアウトも所属もない。

### 本物の認証につなぐときに、必ず直すこと

- 入口（`app/api/v2/session/route.ts`）の ID の発行の流れは、ログインのない試作用。作り直す
  - 「面談がまだない人」の合言葉を捨てない
  - ログインのたびに合言葉を発行し直す（他人が用意した ID を使わされることを防ぐ）
- 回数の上限を、送信元ごと・利用者ごとにする
- 操作の記録に残す ID は、名前やメールアドレスではなく、意味を持たない ID にする
- 1人が複数の会社に所属する場合の扱い、認証の強さ（多要素認証を通ったか）を、権限確認に加える
- 面談の処理（`service.ts`）を、権限確認を通さずに呼べない作りにする（いまは約束事で守っている）

## データの流れ（実際に使うときの形）

```text
ブラウザ ──(HTTPS)──> アプリのサーバー ──> 保存先（DB）
                          │                  └─> バックアップ
                          ├─> 認証サービス（本人の確認）
                          ├─> 外部の AI（面談の返事・資料の下書き）
                          └─> 操作の記録（本文なし）
資料の下書き ──> 本人が印刷して、自分で相談先へ持っていく（自動送信・共有 URL はなし）
```

| 送り先 | 送るもの | 送らないもの |
| --- | --- | --- |
| 認証サービス | ログインに必要な情報 | 面談・資料の中身 |
| 保存先 | 面談、整理した項目、準備リスト、資料の下書き、次の一歩 | パスワード、認証コード |
| 外部の AI（面談） | 本人が入力した会話の、必要な部分だけ | ほかの人の情報、資料用の選択 |
| 外部の AI（資料） | 本人が「載せる」を選んだ項目だけ | 選ばなかった項目、会話の原文 |
| 操作の記録 | いつ・誰が・どの種類の操作を・成功したか | 回答、資料の文章、合言葉 |

## 守るものと、起こり得る事故

| 事故 | いまの備え | 段階3で足すもの |
| --- | --- | --- |
| 別の会社の面談・資料を見られる | 権限確認で断る。あるかどうかも教えない（SEC-01） | 保存先の側でも会社ごとに分ける |
| 同じ会社の別の人・運営担当者に見られる | 本人以外は断る（SEC-02） | 保守で見る必要があるときの承認・期限・記録 |
| 選ばなかった情報が資料に混ざる | 選んだ項目だけを取り出して渡す（SEC-03） | 本物の AI の返事の検証 |
| ログアウト後や退職後も操作できる | 毎回、いまの所属と役割を確かめる（SEC-04） | 認証サービスでの失効・再認証 |
| 面談の中の「指示」に AI が従う | 権限は AI に任せず、サーバーで決める | 本物の AI での試験（SEC-05） |
| 消したはずの情報が戻る | 発言を消すと記録からも消える | バックアップからの復元時に、消去をやり直す（SEC-06） |
| 管理者のアカウントを乗っ取られる | — | 管理者は多要素認証を必須にする |
| 記録や AI の送信先に機密が残る | 記録に本文を出さない | AI の保存期間・学習利用の条件を確認 |

## 検証用の動かし方（Clerk でログイン＋2.0 専用の Turso）

動かし方は `lib/v2/mode.ts` が決める。環境変数を読むのは、2.0 の中ではこのファイルだけ。

| 動かし方 | いつ | ログイン | 保存先 |
| --- | --- | --- | --- |
| 手元（local） | 開発用に動かしているとき（指定なし） | なし | メモリ |
| 検証用（verify） | 下の6つがすべてそろったとき | Clerk | 2.0 専用の Turso |
| 止める（off） | それ以外（ハッカソン版の本番サイトは、これ） | — | — |

検証用にするための設定（**2.0 の検証用の Vercel プロジェクトにだけ入れる。ハッカソン版のプロジェクトには入れない**）：

| 名前 | 中身 |
| --- | --- |
| `V2_MODE` | `verify` |
| `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` | Clerk の公開用の鍵 |
| `CLERK_SECRET_KEY` | Clerk の秘密の鍵 |
| `V2_TURSO_DATABASE_URL` | 2.0 専用の Turso の接続先 |
| `V2_TURSO_AUTH_TOKEN` | 2.0 専用の Turso の鍵 |
| `V2_APP_ORIGIN` | 検証用の公開先（https で始まる、サイトの場所だけ）。Clerk が、このサイト宛てのログインだけを受け付けるために使う |

- 検証用と指定されているのに設定が足りないときは、手元の動き（ログインなし）には落とさず、止める
- ハッカソン版のデータベースと同じ場所が指定されていたら、使わずに止める（書き方や大文字小文字が違っても、ホスト名で見分ける）
- 接続先に鍵や指定を埋め込んだ形は、受け付けない
- 新しく始める回数の上限は、利用者ごと（1人につき1分に5回）。検証用の保存先に置ける面談は200件まで

### 検証用を有効にする前に、必ず済ませること

- **Clerk の側で、登録できる人を限る**（招待した人だけ、または許可したメールアドレスだけ）。
  アプリの側には、登録する人を絞る仕組みがない。限らないまま公開すると、URL を知った人がだれでも登録できる
- 鍵と設定は、2.0 の検証用の Vercel プロジェクトにだけ入れる
- Clerk の処理が動くのは、検証用のときの 2.0 の画面と API だけ（リポジトリ直下の `proxy.ts` が、対象を `/v2` と `/api/v2` に限っている）。ハッカソン版の画面と API は通らない
- ログインした本人ひとりが、ひとつの会社として扱われる。会社に複数の人が所属する形、運営担当者の役割、多要素認証を通ったかの確認は、まだ作っていない
- 検証用は、どの会社も1つのデータベースを使う（行は会社と本人の ID で絞る）。会社ごとにデータベースを分けるのは、実データを扱う前に行う
- AI は、検証用でもモックのまま（外部の AI にはつながない）

**確かめたこと**：鍵がない環境（手元の開発、公開用に組み立てたもの）では、これまでどおり動く・止まること（実際に起動して確認）。検証用の入口は、ログインを偽物に差し替えたテストで確かめた。「ログアウトするとすぐに読めなくなる」「別の人からは見えない」も、偽物でのテストの結果。
**確かめていないこと**：本物の Clerk でのログイン（ログアウト後に使えなくなるまでの時間、ログイン後の移動先、入れ子の枠での動き、読み込み時の通信の有無を含む）、本物の Turso への保存、リクエストの入口（`proxy.ts`）が実際に 2.0 の画面と API だけに掛かること。鍵を入れてから、実際に動かして SEC-01〜07 をやり直す。

## 保存先（Turso）の作り

- 目指す形は、**会社ごとにデータベースそのものを分ける**こと。保存先の部品はその形に対応している。ただし検証用は、いまは1つのデータベースを使う（行は会社と本人の ID で必ず絞る）。会社ごとに分けるのは、実データを扱う前に行う
- Turso には行ごとの権限制御がない。同じ会社の中の「本人だけが見られる」は、アプリ側の権限確認（`lib/v2/access.ts`）で守る
- 保存するときに、持ち主の記録が置き場所と合っているかを確かめる。合わなければ保存しない
- 同じ面談を別の画面や別のサーバーが同時に変えたときは、版の番号で気づき、上書きしない（「読み込み直してください」と伝える）
- 消して作り直した面談に、消す前の古い内容を上書きさせない（作成ごとの印で見分ける）
- 会社と本人の ID は、英数字・「_」・「-」だけを受け付ける
- 保存した中身が壊れていても、本人が「すべて消す」で消せる
- 会社の ID から接続先を決める部分（まだ作っていない）は、ID を URL や名前に文字として埋め込まず、登録済みの会社の一覧から引く。一覧にない会社は断る
- Turso 用の保存先には、保存期間がまだない（件数の上限は、検証用では200件）。実データを扱う前に決める
- **ハッカソン版のデータベースと鍵は使わない。** 2.0 専用のものを新しく作る。環境変数の名前も別にする

### 本物の Turso につなぐまでに必要なこと

1. オーナーが、2.0 専用の Turso のデータベース（検証用。架空の会社2つ分）と鍵を作る
2. 2.0 の検証用の Vercel プロジェクトを、ハッカソン版と別に作り、鍵をそこにだけ入れる（鍵の入力はオーナーが行う）
3. 認証サービスを決めてつなぐ（Turso にはログインの機能がない）
4. 会社が増えたときにデータベースを自動で作る仕組み、保存期間と削除、バックアップからの復元時の消去のやり直しを作る
5. 本物の Turso で、SEC-01〜07 をやり直す

## 決めること（オーナーの判断）

1. **認証サービス**：Clerk に決定済み（2026-11-15）。本番で多要素認証を使うには、有料のプランが必要
2. **検証用の環境の置き場所**：ハッカソン版と別のプロジェクトにする（鍵・DB・公開先を分ける）
3. **外部の AI に送ってよい条件**：保存期間、学習への利用、国外での取り扱いを確認し、利用者への説明文を用意する
4. **保存期間と削除の期限**、バックアップを残す期間
5. **責任者**：運営の責任者、事故のときの連絡先と判断する人
6. **第三者の診断の依頼先と費用**、個人情報の専門家

料金や無料枠は変わるので、選ぶ時点の公式の情報で確かめる。このメモには金額を書かない。

## 実データを扱う前の条件（変わらない）

Notion「05｜TSUGU AI 2.0」の「実データ利用の公開判定」の7項目がすべてそろうまで、実在の事業者の情報を受け付けない。
架空データでの試作や、この段階の検証に合格しても、実利用の承認にはならない。
